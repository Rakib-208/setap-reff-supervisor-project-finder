# Maintenance and troubleshooting

This guide keeps the academic prototype reproducible without requiring
knowledge of every implementation detail.

## Routine local start

From the repository root:

```powershell
.\.venv\Scripts\python.exe manage.py migrate
.\.venv\Scripts\python.exe manage.py seed_demo
.\.venv\Scripts\python.exe manage.py runserver
```

The repeatable seed command restores the expected fictional accounts, profiles,
15 interests and 10 project ideas. It can be run again after experimenting with
staff create/edit/delete functions.

## Verification before a demonstration

Run:

```powershell
.\scripts\verify.ps1
```

This checks Django configuration, confirms there is no uncommitted model
migration, runs all automated tests and enforces at least 95% coverage. The
same checks run in GitHub Actions for branches and pull requests.

Then manually confirm:

1. Student login reaches `/staff/`.
2. Name search and interest filtering return expected profiles.
3. Staff login reaches `/dashboard/`.
4. One create/edit/delete operation displays feedback and persists.
5. The interface has no horizontal scrolling at the intended recording width.

## Changing a model

1. Edit `finder/models.py`.
2. Create a migration with `python manage.py makemigrations finder`.
3. Read the generated migration before applying it.
4. Run `python manage.py migrate`.
5. Add or update model/form/view tests.
6. Run the complete verification script.

Never edit an already-applied migration merely to hide a model difference.

## Updating seed content

Edit the clearly fictional records in
`finder/management/commands/seed_demo.py`, then update seed-command assertions
if counts change. Keep all emails under `.test`, avoid identifiable real people
and retain the published Student and Staff demonstration credentials unless the
report and demo script are updated at the same time.

## Common problems

### Login reports incorrect credentials

Run `python manage.py seed_demo`, then use the exact email and password printed
in the README. Passwords are case-sensitive and end with a full stop.

### A Student sees Access denied

Student and Staff routes are intentionally separate. Sign out and choose the
account matching the workflow. A wrong-role response is expected security
behaviour, not a broken link.

### The database reports a missing table or column

Run `python manage.py migrate`. If `makemigrations --check --dry-run` reports a
change, create and review the missing migration rather than modifying SQLite
manually.

### Port 8000 is already in use

Stop the other development server or start this one on an explicit alternative:

```powershell
.\.venv\Scripts\python.exe manage.py runserver 127.0.0.1:8001
```

### Styling appears stale

Perform one normal browser refresh. The development server serves the current
app static files; no frontend build step is required.

## Local database backup

The ignored `db.sqlite3` file contains only local demonstration state. When a
specific customised demo state matters, close the development server and copy
that single file to a clearly named local backup outside the repository. Do not
commit the database because it contains session state and is regenerated by
migrations plus `seed_demo`.

## Security boundary

Before any deployment beyond the local assessment:

- provide a private `DJANGO_SECRET_KEY`;
- set `DJANGO_DEBUG=false`;
- restrict `DJANGO_ALLOWED_HOSTS`;
- use HTTPS and review secure-cookie settings;
- rotate or remove demonstration accounts;
- replace fictional content with approved data processes only;
- review the database, backups, logging and concurrent usage;
- complete institutional security, privacy and accessibility assessment.

See `SECURITY.md` for the concise repository notice.

## Git workflow

Use a linked issue, a short-lived branch, focused commits and a pull request.
Commit messages should describe an observable change, not simply “update”.
Keep generated coverage output, local databases and virtual environments out of
Git; the existing `.gitignore` already excludes them.
